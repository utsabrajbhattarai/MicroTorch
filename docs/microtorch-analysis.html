01 Repository Overview

A one-way dependency stack: an engine that knows nothing but linear algebra, two thin demos that link it, and two GUIs decoupled from both through CSV files.

Top-level map

Folder / filePurpose
include/microtorch/Public headers — the API surface. One subfolder per concern: ops/, optim/, gnn/, diffusion/, data/, eval/, gui/, plus core Tensor.hpp, gradient_check.hpp, logger.hpp.
src/Implementations, compiled into one static library libmicrotorch. This is the engine.
app/Thin executables: gnn_train.cpp, diffusion_train.cpp, and app/gui/ (two raylib programs + a CSV loader). Apps stay short so the engine is visibly doing the work.
tests/Catch2 suite, one file per op, wired 1:1 with src/. Every op carries a finite-difference gradient check.
frames/Four pre-baked diffusion animations (spiral, two-moons, heart, infinity), 251 frames × 1000 points each — what the diffusion viewer reads.
gui_artifacts/The four CSVs the GNN dashboard reads: nodes, edges, accounts, metrics.
data/Elliptic Bitcoin dataset, held locally (gitignored). 203,769 nodes · 234,355 edges · 166 features · ~46k labeled · ~1:11.5 imbalance · ~95% AUROC GCN baseline.

Architecture in three layers

ENGINE (libmicrotorch) DEMOS (apps) GUIs (raylib) Tensor · autograd · ops · optim → gnn_train.cpp → gnn_dashboard.cpp ← gui_artifacts/*.csv models · data loaders · eval → diffusion_train.cpp → diffusion_viewer.cpp ← frames/*.csv

The arrows point one way only. The engine depends on nothing but Eigen; the apps depend on the engine; the GUIs depend on neither — they are decoupled through the filesystem and link only raylib. That is the README's "engine is the product" claim made structural: the GNN and diffusion demos are built from the same op set with no engine-side special-casing, and the GUIs cannot reach back into the engine at all.

02 Per-file Breakdown

Grouped by concern. Each entry: what it is, what it defines, and the design decision worth knowing.

Engine core

include/microtorch/Tensor.hppthe core value type

Defines class Tensor with four public fields — data, grad, parents, backward_fnc — plus zero_grad() / backward(), the TensorPtr alias (L12) and the make_tensor() factory (L37). Fields are public because a Tensor is an autograd node every op mutates directly; encapsulation would be pure friction.

src/Tensor.cppthe backward pass

backward() (L15–40): a recursive DFS build_topo yields a post-order topological list, seeds the root with grad.setOnes() (L32), then walks it in reverse firing each node's backward_fnc. A visited-set of raw pointers avoids revisiting shared subgraphs.

gradient_check.{hpp,cpp}numeric verification

gradient_check(loss_fn, input, eps) runs the analytic backward, then central-differences each element (cpp:L37) and returns the max discrepancy. loss_fn is a std::function<TensorPtr(TensorPtr)> — the mechanism that wraps a whole model+loss as one scalar function.

ops.hpp · logger.{hpp,cpp}umbrella + utility

ops.hpp includes all eight ops. log_training_csv(path, losses) writes an epoch,loss CSV; referenced only by its own test.

Ops — each is a forward plus a captured backward lambda

Every op follows one template: assert shapes → compute Eigen forward → make_tensor → set parents → capture raw pointers and assign backward_fnc. The raw-pointer capture is deliberate (see §3).

FileForwardBackward it registers

matmul.cppa * b (Eigen)a.grad += out.grad·bᵀ; b.grad += aᵀ·out.grad
broadcast_add.cpp(M,N)+(1,N) bias adda.grad += out.grad; b.grad += out.grad.colwise().sum()
relu.cppmax(0, a)grad × (a > 0) mask

mse_loss.cpp‖pred−target‖²/size(2/size)·(pred−target); target captured by value

mse_loss captures target by copy (L37–38) precisely because it is a stack reference that would dangle by backward-time. softmax_cross_entropy is overloaded — a masked 4-arg version and a 2-arg convenience wrapper that calls it with an all-ones mask (L58–62); fusing softmax with cross-entropy yields the Jacobian-free P−Y gradient.

Optimizers updated · now an inheritance hierarchy

optim/optimizer.hppabstract base class

class Optimizer (L10) — the base for every optimizer. Owns the parameters (protected std::vector<TensorPtr> params_), provides a shared concrete zero_grad(), declares virtual void step() = 0 (pure virtual → abstract, cannot be instantiated) and a virtual ~Optimizer() = default so deletion through an Optimizer* is safe.

optim/sgd.{hpp,cpp}

class SGD : public Optimizer — adds lr_, delegates construction with : Optimizer(params), and void step() override does w -= lr·grad. zero_grad() is inherited from the base.

optim/adam.{hpp,cpp}

class Adam : public Optimizer — adds moment buffers m_/v_ (sized per parameter in the ctor) and beta1_/beta2_/eps_/t_; step() override is a textbook bias-corrected Adam update. Both optimizers hold shared_ptrs to the same tensors the forward pass reads.

Models

gnn/gnn_model.{hpp,cpp}2-layer GCN + linear head

Private weights, public forward(A, X, use_graph) / parameters(). Each layer is neighbor_aggregation (if use_graph) → matmul → broadcast_add → relu; the classifier omits ReLU for raw logits. The use_graph=false path skips aggregation — that single boolean is the GNN-vs-MLP ablation.

diffusion/diffusion_model.{hpp,cpp}MLP denoiser + forward_noise

A 3-layer MLP, plus free function forward_noise implementing the DDPM blend x_t = √ᾱ·x0 + √(1−ᾱ)·noise (L9–30). Has its own duplicate he_init. stale header comment still says in_features = 3, but the app now feeds width-10 embedded input.

diffusion/noise_schedule.{hpp,cpp}

struct NoiseSchedule (public T, beta, alpha, alpha_bar) built from a linear β and cumulative-product ᾱ, with alpha_bar[0] = alpha[0].

Data loaders

data/toy_data.{hpp,cpp}

Seven 2D generators, all seeded mt19937(42): make_spiral (tight double-spiral, r ≤ 2, θ = 3π·t), make_light_spiral (loose t·cos t over 4π), two-moons, infinity, concentric-circles, heart, checkerboard.

data/data_loader.{hpp,cpp}the Elliptic pipeline

load_csv, load_labels ("1"→illicit, "2"→licit, else −1), build_txid_index, load_edges, and orchestrator load_elliptic (L199–302): drops the first two feature cols, one-hot encodes Y, builds a symmetric adjacency with self-loops via a dedup set, then applies symmetric normalization D^(−½) A D^(−½) (L285–296) so high-degree nodes don't explode. Yields EllipticData{A, X, Y, labeled_rows}.

Eval & GUI export

confusion_counts, precision, recall, f1_score, accuracy, and a rank-based auroc with tie-averaged ranks (cpp:L64–73). inconsistency declared in the global namespace, unlike the rest of the engine.

03 The Engine's Core Abstractions

How the autodiff actually works — the intellectual center of the project, told as one story.

A tensor is a node in a computation graph. Every Tensor carries its value (data), a same-shape gradient accumulator (grad, zero-initialized), the tensors it was computed from (parents), and a closure describing how to push gradient to those parents (backward_fnc). Tensors live behind shared_ptr so the graph stays alive as long as anything downstream references it.

An op builds one node and teaches it to differentiate itself. matmul(a,b) computes out.data = a.data * b.data, records out.parents = {a,b}, and assigns out.backward_fnc a lambda that later does a.grad += out.grad·bᵀ and b.grad += aᵀ·out.grad. It doesn't compute a gradient now — it stores a recipe. The key inversion: the backward pass is data (a list of closures), not control flow.

Why raw pointers in the lambdas

Each op captures a.get() — raw, never shared_ptr. out owns its backward_fnc, and out.parents already keeps a/b alive. If the lambda also held shared_ptrs, out would transitively own itself — a reference cycle and a leak. Raw capture lets the closure touch grad without owning anything; parents guarantees the pointers stay valid until the whole graph drops. mse_loss is the lone by-value capture, because target isn't a graph node.

A forward pass composes ops into a DAG. When GNNModel::forward chains neighbor_aggregation → matmul → broadcast_add → relu, each call allocates a tensor whose parents point back at its inputs. By the final logits you have a DAG: leaves are parameters and input, root is the loss scalar. No gradients yet — only structure and recipes.

Backward is a topological replay. Tensor::backward() does a post-order DFS to list every node parents-before-children, seeds dL/dL = 1 with grad.setOnes(), then iterates in reverse so each node runs only after everything that consumes it. Each backward_fnc +=-accumulates into its parents' grad — so a tensor used in two places correctly receives the sum of both paths. When it finishes, every parameter's grad holds ∂loss/∂param.

The optimizer closes the loop. An Adam/SGD holds shared_ptrs to the same parameters. zero_grad() clears; forward rebuilds a fresh graph; backward() fills; step() mutates data. A new graph each iteration is why the accumulate-with-+= design is safe.

Verification is first-class. Because a correct backward is the whole value proposition, gradient_check wraps forward+backward as a std::function and compares analytic gradients against central differences — and a test feeds it a deliberately broken ReLU to prove the harness catches wrong gradients. That's the safety net the README leans on: a wrong derivative surfaces as a named test failure, not a model that mysteriously never learns.

04 The Two Demos

Both are built from the same op set — one supervised classifier on a real graph, one generative model on synthetic 2D shapes.

GNN pipeline — anti-money-laundering

  1. Load Elliptic via load_elliptic → normalized sparse A, features X (N×166), one-hot Y, labeled_rows.
  2. Split (per seed): separate illicit/licit, shuffle, 80/20 — stratified, so the ~1:11.5 imbalance survives in both sets. Build train/test masks.
  3. Train: GNNModel(166,128,2), Adam(0.01), 70 epochs masked softmax-CE; test loss printed every 10 epochs.
  4. Evaluate: final forward, TP/FP/TN/FN over test rows (illicit when logit₁ > logit₀), precision/recall/F1/accuracy, AUROC via the Mann-Whitney rank statistic.
  5. Ablation: identical run with use_graph=false — a plain MLP on node features, isolating the graph's contribution. Repeated over 3 seeds.
Finding

Both the GNN and the MLP ablation land in the ~0.96–0.98 AUROC range across seeds — near the ~0.95 published GCN baseline the data README says to sanity-check against. The graph's marginal gain over the plain MLP was small on this feature set (the Elliptic node features are already highly predictive) — a legitimate ablation result, not a failure.

Diffusion pipeline — 2D generative

  1. Target: make_spiral(1000).
  2. Schedule: make_noise_schedule(T=1000) → linear β, cumulative ᾱ.
  3. Forward noising: forward_noise blends x0 with Gaussian noise at random t, returning the exact noise as the training target.
  4. Time embedding: build_input concatenates x_t with 8 sinusoidal features → width-10 input, so the MLP can tell noise levels apart.
  5. Train: DiffusionModel(10,256,2) predicts noise; MSE averaged over 16 timesteps/epoch; Adam, 2000 epochs.
  6. Sample (DDPM): from pure noise, iterate t=T-1…0 applying the reverse mean update, snapshotting frames every 4th step.
  7. Export: frames.csv (animation) + generated.csv (final).
x ← (1/√αₜ)·(x − βₜ/√(1−ᾱₜ)·ε̂) + √βₜ·z (z ~ 𝒩(0,I) for t>0, deterministic at t=0)
Finding

The plain MLP fits the loose make_light_spiral cleanly but struggles on the tight make_spiral, producing a blob rather than sharp arms — a modeling-capacity limit, not a bug. The curated animations in frames/ are what the viewer showcases.

05 The GUIs

Two raylib front-ends, each reading only CSV artifacts — no engine linkage.

GNN dashboard — gnn_dashboard.cpp

An AML analyst view. It loads gui_artifacts/{nodes,edges,accounts,metrics}.csv through the GUI-side loader. Left column: a data-preview table, a paginated ranked-accounts table (click to select; Prev/Next; risk as a percentage), and a metrics panel. Right: an interactive ego-graph of the selected account — counterparties split spatially into received (left arc) and sent (right arc), each capped at the 8 riskiest, drawn with directional arrows and colored red/green by predicted label. Diffusion viewer — diffusion_viewer.cpp

A tiny two-screen state machine. The menu renders four shape cards in a 2×2 grid, each with a live mini-preview of that shape's final frame; clicking loads its full animation. Both screens share one to_screen mapping that flips y. It reads the curated frames/ files — not the root frames.csv a fresh training run writes.

06 OOP Inventory

All five pillars are present. The optimizer hierarchy supplies real inheritance and virtual dispatch; the ops deliberately use type erasure instead of a class hierarchy. The defense strength is being able to say which pattern each subsystem uses, and why.

PillarWhere it lives (with the defense line)
EncapsulationGNNModel, DiffusionModel, SGD, Adam — private members, public methods; the Optimizer base keeps params_ protected so subclasses reach it but callers can't. Deliberate non-encapsulation: Tensor exposes data/grad/parents/backward_fnc as public fields (Tensor.hpp:15–21) because it's an autograd node every op mutates and there's no invariant to protect. Being able to justify Tensor's public fields is a strong point.
Inheritance now presentclass Optimizer (optimizer.hpp:10) is an abstract base; class SGD : public Optimizer (sgd.hpp:7) and class Adam : public Optimizer (adam.hpp:8) derive from it, delegate construction with : Optimizer(params), and override step(). Textbook use: the base holds the shared state (params_) and shared behavior (zero_grad()); the one operation that differs (step()) is deferred to the subclasses.
PolymorphismThree distinct forms. (1) Virtual dispatch: virtual void step() = 0 (optimizer.hpp:26) overridden per optimizer, plus a virtual ~Optimizer() for safe deletion through a base pointer. (2) Overloading: softmax_cross_entropy masked/unmasked (hpp:L10–11). (3) Type erasure: std::function<void()> backward_fnc — each op installs a different callable behind one interface. candid the demos instantiate Adam concretely, so no call currently dispatches through an Optimizer* — the machinery exists; the polymorphic call site doesn't yet.
AbstractionTensorPtr + make_tensor hide shared_ptr; each op abstracts a forward/backward pair behind a call; the Optimizer base is itself an abstraction (can't be instantiated — it defines the interface "an optimizer has step() and zero_grad()"); load_elliptic abstracts a multi-file ETL.
Composition the backboneModels have-a set of parameter TensorPtrs; Adam has-a vector of params + moment matrices; a Tensor has-a vector<TensorPtr> parents — the graph itself is composition; forward passes are literal function composition of ops.
The one-sentence defense

"Optimizers share state and one differing operation, so they get a base class with a pure-virtual step(); ops are stateless recipes, so they get std::function type erasure instead of a parallel Op hierarchy — same behavioral polymorphism, no wasted class tree." That answer turns the apparent inconsistency into evidence of judgment.

07 Test Coverage

One Catch2 file per component, each ctest a named entry. Strong on op-level correctness; thin on integration.

What's verified

  • Every op: hardcoded forward + analytic backward + finite-difference check < 1e-6 — matmul, broadcast_add, relu, reduction, mse_loss, neighbor_aggregation, softmax_cross_entropy (both overloads, incl. a proof that unlabeled rows get exactly zero gradient).
  • The harness itself: passes a correct op and catches a broken one.
  • Models end-to-end: GNNModel and DiffusionModel full forward/backward via gradient_check.
  • Optimizers: SGD and Adam converge on f(x)=x² (constructed as concrete types).
  • Diffusion math: forward_noise blend + edge cases; schedule β linearity and ᾱ monotonic product.
  • Data: csv, labels, txid-index, edges, full load_elliptic assembly on synthetic files. Toy shapes: bounds for spiral, moons, infinity, circles, heart, checkerboard. Eval/export/logger: confusion/f1/accuracy; the four CSV writers; the logger.

08 Observations

Honest and specific — the things an examiner is most likely to probe. Keyed by type. The GUI-export path has since been fixed and merged, so the items that were once red/amber now lead as resolved; the standing observations follow.

  1. resolvedThe GUI-export path is now live and wired in.

    gnn_train.cpp calls export_gui_artifacts at the end of a run (L214), which fans out to export_all_gui_artifacts; EllipticData now carries the raw_edges and tx_ids the exporter needs (data_loader.hpp:24–25). The four gui_artifacts/*.csv are regenerated from the trained model every run, not hand-shipped from another branch.

  2. resolvedwrite_edges_csv now agrees with edges.csv.

    The writer keeps the real txId1 → txId2 order (gui_export.cpp:14–18); the old edge.first < edge.second filter that dropped direction and ~half the edges is gone. The exported edges.csv is fully directed and matches the model's adjacency, so the dashboard's incoming/outgoing arrows are correct.

  3. resolvedOne AUROC implementation, not two.

    gnn_train.cpp now calls the shared eval_metrics::auroc (L201) — the same tie-averaged function write_metrics_csv uses — so the console AUROC and the metrics.csv AUROC can no longer drift. The local sequential-rank compute_auroc is gone.

  4. resolvedEngine headers now share the microtorch namespace.

    eval_metrics and gui_export — headers and .cpp bodies — now live in namespace microtorch like the rest of the engine, verified compiling with symbols microtorch::auroc / microtorch::write_edges_csv. No more global-namespace outliers.

  5. resolvedDenoiser header comment matches the code.

    diffusion_model.hpp now documents in_features = 10 (L24), matching the width-10 embedded input the app feeds; the stale (n, 3) shape note is gone.

  6. by designThe diffusion viewer reads curated frames, not live training output.

    Deliberate: the viewer showcases the four polished animations in frames/frames_*.csv, while diffusion_train writes root frames.csv. Auto-loading a freshly-trained shape is an unbuilt convenience — a coverage gap, not a defect — so copy the file in to preview a new run.

  7. couplingThe CSV schema is still defined twice.

    The engine's gui_export structs and the GUI's csv_loader structs independently describe the same columns (with type differences — account_id string vs long long). The drift it once caused — edge direction — is now fixed, but the duplication remains: a single shared schema or generated header would remove the whole class of bug.

  8. by designmake_spiral vs make_light_spiral.

    The app targets the tight spiral the plain MLP can't fit well; the loose one produces a clean spiral. A capacity limit, not a bug — state it plainly if the demo looks blobby.

  9. assumptionbackward() assumes a scalar root.

    grad.setOnes() is only correct because every entry point is a 1×1 loss. Calling backward on a non-scalar would seed the wrong upstream gradient.

  10. assumptionRe-running backward() would double-count.

    Grads accumulate with += and only parameters are zeroed (by the optimizer). Safe only because a fresh graph is built each iteration.

  11. minorDuplicated he_init.

    Both gnn_model.cpp (L12) and diffusion_model.cpp (L33) define their own static He-init with independent static mt19937 streams.

09 Defense-Worthy Questions

A rehearsal set — overview and rationale questions, not just flaw-hunting. Each answer is short enough to say out loud and grounded in the code above.

Overview & rationale

QWhy build automatic differentiation from scratch instead of using PyTorch or TensorFlow?

The engine is the deliverable — the project demonstrates understanding of reverse-mode AD, not model tuning. A framework would hide exactly the mechanism being assessed. Eigen is used only for linear-algebra storage and matrix ops, never for gradients.

QWhy reverse-mode rather than forward-mode AD?

The loss is a single scalar and the parameters are many. Reverse-mode computes all ∂loss/∂param in one backward pass (cost ≈ one forward); forward-mode would cost one pass per input dimension. For neural nets that's the standard, and correct, choice.

QIn one breath, how does a value remember how to differentiate itself?

Each Tensor stores its parents and a backward_fnc closure that pushes gradient to those parents. backward() topologically orders the graph from the loss and replays those closures in reverse. The backward pass is data, not hand-written control flow.

QWhat do the GNN and diffusion demos prove about the engine?

That it's a genuine framework, not a one-architecture hack: a graph classifier and a generative denoiser are built from the same eight ops with zero engine-side special-casing. If both train, the abstraction is real.

Design decisions

QWhy capture raw pointers in the backward lambdas instead of shared_ptr?

To avoid a reference cycle. out owns its backward_fnc, and out.parents already keeps the inputs alive; if the closure also held a shared_ptr to out, out would own itself and leak. Raw capture touches grad without owning anything. mse_loss is the exception — it captures target by value because it isn't a graph node.

QWhy is Tensor's data public but the models' weights private?

Tensor is a plain autograd node every op reads and writes — there's no invariant to protect, so getters would be ceremony. A model owns an invariant (a fixed, specifically-initialized parameter set), so it hides that behind forward() and parameters(). Encapsulation follows whether there's something to protect.

QYou use an inheritance hierarchy for optimizers but type erasure for ops. Isn't that inconsistent?

It's deliberate, and it's the crux of the OOP story. Optimizers share state (params_) and shared behavior (zero_grad) and differ only in step() — a textbook base class with a pure-virtual method. Ops are stateless recipes with nothing to share; wrapping each in an object with a virtual backward() would add a parallel class tree and heap allocation for no benefit, so they use std::function. Same behavioral polymorphism, right tool per shape.

QWhy fuse softmax and cross-entropy into one op?

Two reasons. Numerical stability — the forward subtracts the row max before exponentiating. And the gradient collapses to P − Y with no Jacobian, which is cheaper and far less error-prone than composing a separate softmax and log.

QWhy symmetrically normalize the adjacency (D^-½ A D^-½)?

Neighbor aggregation sums feature rows, so without normalization a high-degree node produces huge activations and training destabilizes. Symmetric normalization (the GCN scheme) bounds the scale and accounts for the degree of both endpoints. Self-loops are added first so a node keeps its own features.

QWhy a sinusoidal time embedding instead of feeding the scalar t?

A single t/T column is a weak conditioning signal; the MLP couldn't distinguish noise levels and the loss plateaued. Multi-frequency sin/cos features (like transformer positional encoding) give the network an expressive basis for the timestep, which broke the plateau.

QWhy pass CSV artifacts between the engine and the GUIs instead of linking?

Decoupling. The GUI has no build- or run-time dependency on the engine, can be developed and run independently, and the heavy raylib dependency stays out of the engine and its tests. The acknowledged cost is that the CSV schema is defined twice (writer and reader) — a drift risk that, honestly, once bit the edge-direction field.

Correctness, limits & candor

QHow do you know your gradients are actually correct?

Every op has a central-difference gradient check under 1e-6, whole models (GNN and diffusion) are gradient-checked end-to-end, and the harness is itself tested against a deliberately broken ReLU — so we've shown it catches wrong gradients, not merely that it passes correct ones.

QDid the graph actually help? What does the ablation say?

Both the GNN and the MLP ablation reached ~0.96–0.98 AUROC across three seeds, near the ~0.95 baseline; the graph's marginal gain was small here because the Elliptic node features are already highly predictive. That's a real, defensible finding — the ablation exists precisely to measure that contribution honestly rather than assume it.

QWhat happens if backward() is called twice, or on a non-scalar output?

Gradients accumulate with +=, so a second backward on the same graph double-counts — safe only because each iteration builds a fresh graph and the optimizer zeroes parameters first. And backward() seeds grad.setOnes() assuming a 1×1 loss; a non-scalar root would seed the wrong upstream gradient. Both are conscious constraints, not accidents.

QDo you ever actually call an optimizer through the Optimizer base pointer?

Not yet — the demos construct Adam concretely. The base gives us the shared zero_grad, the abstract interface, and the ability to write code over an Optimizer&; the virtual dispatch is in place but no polymorphic call site exercises it. Worth stating up front rather than being caught on it.

QWhat's the single biggest weakness you'd flag yourself?

The engine/GUI schema duplication (§8): the same CSV columns are described independently on the write and read sides, and that's where the edge-direction bug slipped in.
